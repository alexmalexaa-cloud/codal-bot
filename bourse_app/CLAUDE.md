# بورس‌یار — داشبورد محلی تحلیل سهام بورس تهران بر پایه‌ی داده‌های کدال

## هدف
برنامه‌ی وب «محلی» که روی کامپیوتر شخصی اجرا می‌شود (نه روی سرور اینترنتی).
ظاهرش داشبورد مدرن است و با سرور کوچک Flask روی localhost اجرا می‌شود.
بعداً اسکریپت‌های پایتون به کدال (codal.ir) وصل می‌شوند، داده‌ها را جمع‌آوری
و در SQLite ذخیره می‌کنند و در همین رابط نمایش می‌دهند.

**ترتیب کار:** اول ظاهر کامل و نهایی (با داده‌ی نمونه که برچسب «داده‌ی نمونه» دارد)،
بعد کدهای پایتون جمع‌آوری داده.

## اجرا
```
python -m pip install flask
python app.py        # سپس: http://127.0.0.1:5000

python scrape.py symbols              # لیست نمادها (یک بار کافی است)
python scrape.py all فولاد            # گزارش‌های ماهانه + صورت‌های مالی نماد
python scrape.py show فولاد           # خلاصه‌ی داده‌های ذخیره‌شده
python scrape.py --delay 3 monthly فولاد --limit 48   # کندتر و بیشتر
```
سیستم کاربر ویندوز است (پایتون ۳.۱۳). python app.py بدون Debug اجرا می‌شود (سریع‌تر، کارهای در جریان با تغییر
فایل‌ها از دست نمی‌روند). برای توسعه با راه‌اندازی دوباره‌ی خودکار: `set BOURSE_DEBUG=1` (پورت: BOURSE_PORT).
فایل‌های static با ?v=زمان تغییر لینک می‌شوند (asset() در قالب‌ها) ← بعد از به‌روزرسانی Ctrl+F5 لازم نیست.

## فناوری
- Python + Flask، قالب‌های Jinja2 (base.html + صفحه‌ها با extends؛ CSS صفحه در {% block head %}،
  اسکریپت صفحه در {% block scripts %})
- HTML + CSS + JavaScript ساده؛ بدون فریم‌ورک و بدون کتابخانه‌ی نمودار
  (همه‌ی نمودارها با HTML/CSS/SVG)
- ذخیره‌ی ورودی‌های کاربر: واچ‌لیست و پرتفوی در SQLite (data/user.db)؛ مدل برآورد سود و یادداشت‌ها در localStorage
- تمام رابط فارسی و راست‌چین (dir="rtl", lang="fa")
- بعداً: pywebview برای پنجره‌ی دسکتاپ و PyInstaller برای ساخت exe

## کارایی و قواعد پیاده‌سازی (بعد از بازبینی کامل پروژه؛ رعایت شود)
- دیتابیس: db.connect سبک است — ساختار/مهاجرت/شاخص فقط بار اول هر اجرا (_prepare)؛ حالت WAL (خواندن صفحه‌ها
  هم‌زمان با نوشتن کار پس‌زمینه بدون قفل)، synchronous=NORMAL، cache 16MB. store.connect هم یک بار مهاجرت.
  هنگام بستن برنامه -wal ادغام می‌شود (atexit)؛ قبل از کپی/پشتیبان‌گیری از data برنامه را ببندید.
- app.py: codal_db() و user_db() در flask.g (یک اتصال در هر درخواست، بسته در teardown)؛ توابع کمکی اتصال نمی‌سازند.
  خطای sqlite ← JSON فارسی 503. JSON بدون مرتب‌سازی کلید و فشرده.
- شاخص‌ها: monthly_reports(symbol, period_end, published) و (period_end)، fin_reports(symbol, consolidated,
  period_end, months, published)، letters(letter_type, period_end) و (symbol, letter_type, period_end).
  نماهای monthly_latest و fin_latest بدون این شاخص‌ها O(n²) بودند (رتبه‌بندی ماهانه در اندازه‌ی کل بازار ۱۹ ثانیه ← ۵۰ میلی‌ثانیه)
- letters.period_end و months از عنوان (text.title_period، هنگام ذخیره) ← پیدا کردن اطلاعیه‌ی یک دوره با شاخص، نه
  خواندن عنوان همه‌ی اطلاعیه‌ها در پایتون. پرس‌وجوی یک ماه: period_end BETWEEN 'YYYY/MM/00' AND 'YYYY/MM/99'
- mrank فقط ردیف‌های ماه‌های لازم را می‌خواند (ماه، ماه قبل، ماه مشابه سال قبل)؛ screener همه‌ی گزارش‌ها را با یک
  پرس‌وجو و صدک‌ها با bisect؛ رتبه‌بندی سود با کلید داده در حافظه (ranking_cached) و پیش‌بینی‌های ML با امضای
  داده‌ی نماد (_ml) نگه داشته می‌شوند. فیلدهای داخلی (pct_*، tracing_no، …) به صفحه فرستاده نمی‌شوند
- tsetmc: بدون executescript در هر فراخوانی (commit ضمنی)؛ IN با تکه‌های ۵۰۰تایی. دریافت هم‌زمان قیمت از چند صفحه ← یکی
- home.js: هر زبانه فقط وقتی دیده می‌شود داده می‌گیرد (whenVisible): با باز کردن عملکرد ماهانه، برآورد سود به
  /api/quarters و کدال درخواست نمی‌فرستد و برعکس
- جستجو و picker: پاسخ دیرتر رسیده‌ی تایپ قبلی نادیده گرفته می‌شود (شماره‌ی درخواست)
- [hidden] همیشه display:none !important (کلاس‌های display:flex مثل .box آن را بی‌اثر نکنند)
- آزمون: هر تغییر بزرگ با مقایسه‌ی خروجی همه‌ی API‌ها (قبل/بعد) و دیتابیس مصنوعی هم‌اندازه‌ی کل بازار
  (۷۰۰ شرکت × ۱۸ ماه + صورت‌های مالی) سنجیده شود


## داده‌های کدال (SQLite: data/bourse.db)
- symbols، letters (همه‌ی اطلاعیه‌های دیده‌شده)، skipped (گزارش‌های قالب قدیمی/ناشناخته)
- monthly_reports + monthly_items (section: domestic/export/service/returns؛ made, sold, price, amount)
- fin_reports (rev, cogs, gross, sga, other_op, op_profit, fin, non_op, pretax, tax, net, eps, capital)
  + fin_lines (همه‌ی ردیف‌ها با عنوان اصلی)
- نماهای monthly_latest و fin_latest: آخرین نسخه‌ی هر دوره (اصلاحیه جایگزین اصلی می‌شود)
- واحدها: مبالغ میلیون ریال (همان کدال؛ ÷۱۰٬۰۰۰ = میلیارد تومان)، هزینه‌ها منفی، EPS ریال
- صورت سود و زیان تجمعی است (۳/۶/۹/۱۲ ماهه)؛ عدد فصلی = تفاضل دو دوره‌ی پشت سر هم
- گزارش‌های خیلی قدیمی datasource ندارند و در skipped ثبت می‌شوند
- کدال سریع محدودیت می‌گذارد (HTTP 429) و بعد از حدود ۱۰ صفحه‌ی گزارش پشت سر هم کپچا نشان می‌دهد؛
  تأخیر را کم نکنید و کپچا را دور نزنید

## حافظه‌ی پاسخ‌های کدال (data/cache.db، codal/client.py)
- همه‌ی درخواست‌ها از client.get_text می‌گذرند؛ پاسخ معتبر فشرده (zlib) ذخیره می‌شود:
  صفحه‌ی گزارش Decision.aspx برای همیشه (FOREVER؛ فقط اگر «var datasource» دارد)، جستجوی اطلاعیه
  صفحه‌ی اول ۳ ساعت و بقیه ۷ روز، لیست شرکت‌ها ۷ روز. کپچا و خطا ذخیره نمی‌شوند
- کدال در دسترس نیست (429 یا خطا) و نسخه‌ی کهنه در حافظه هست ← همان برمی‌گردد
- فاصله‌ی درخواست: جستجو DELAY=۲٫۵ ثانیه، صفحه‌ی گزارش DELAY_REPORT=۴ ثانیه (+ تصادفی تا ۵۰٪)
- کپچا: کاربر کد را خودش وارد می‌کند (برنامه کپچا را حل نمی‌کند).
  صفحه‌ی کپچای کدال (عنوان «تأیید کاربر») تصویر را از POST /ReportsCaptcha.aspx/GetCaptchaImage
  (پاسخ {"d": data-uri}) می‌گیرد و کد را به POST /ReportsCaptcha.aspx/VerifyCaptcha با {"code": …}
  می‌فرستد (پاسخ {"d": true|false})؛ هر دو به کوکی نشست وابسته‌اند (data/codal_cookies.txt، LWPCookieJar)
- کپچا دیده شد ← data/.captcha_at؛ تا تأیید کد (یا ۳۰ دقیقه، CAPTCHA_EXPIRE) صفحه‌ی گزارش تازه‌ای
  درخواست نمی‌شود و client.Captcha برمی‌گردد
- برنامه‌ی وب: کار پس‌زمینه state="captcha" با resume؛ GET /api/captcha، GET /api/captcha/image،
  POST /api/captcha/verify ← کد درست ← کار منتظر همان‌جا ادامه می‌دهد و کارهای مهلت‌گذشته اول صف می‌روند (jobs.resume_after_captcha)؛
  app.js هر ۵ ثانیه می‌پرسد و پنجره‌ی «کد امنیتی کدال» را روی هر صفحه باز می‌کند
  (+ اعلان مرورگر و چشمک عنوان زبانه)؛ Bourse.jobActive = running | queued | captcha
- خط فرمان: ask_captcha() تصویر را در data/captcha.jpg ذخیره و باز می‌کند، کد را از ترمینال می‌گیرد
  و دستور را دوباره اجرا می‌کند
- GET /api/cache؛ python scrape.py cache [--clear-search]
- داده‌های پردازش‌شده هم در bourse.db هستند و گزارش خوانده‌شده دوباره دانلود نمی‌شود (is_done)

## کامل بودن گزارش‌های ماهانه (collect.collect_monthly)
- ماه‌های لازم = ۱۲ ماه سال مالی قبل + سال جاری تا آخرین گزارش (monthly_coverage، fiscal_months)
- اطلاعیه‌ها جدیدترین اول؛ فقط ماه‌های لازمی که نداریم (یا اصلاحیه‌ی جدیدتر) دانلود می‌شوند؛
  وقتی همه موجود شد و به قبل از سال مالی قبل رسیدیم، تمام. (حلقه‌ی عمومی collect هم دیگر با دیدن
  اصلاحیه‌ی یک دوره‌ی قدیمی متوقف نمی‌شود: ۱۲ اطلاعیه‌ی قدیمیِ پشت سر هم لازم است)
- monthly_payload.coverage ← نوار «سال قبل n از ۱۲ · سال جاری تا آخرین گزارش · بقیه پیش‌بینی مدل»؛
  ماه جاافتاده ← بررسی خودکار (با مهلت‌های fresh.py) + دکمه‌ی «تکمیل از کدال»

## اول دیتابیس، بعد کدال (codal/fresh.py) — هر سه بخش
- همه‌ی داده‌های دریافتی در bourse.db (داده‌ی پردازش‌شده) و cache.db (پاسخ خام) می‌مانند؛ صفحه‌ها همیشه
  اول از دیتابیس رندر می‌شوند و فقط اگر داده‌ی لازم نباشد کار کدال ساخته می‌شود
- جدول checks(kind, symbol, checked_at): زمان آخرین رجوع موفق به کدال (jobs._run بعد از کار موفق ثبت می‌کند)
- fresh.monthly: داده نیست ← کدال | ماه جاافتاده ← کدال (خودکار حداکثر هر ۲۴ ساعت) |
  آخرین ماه ذخیره‌شده قبل از ماه گذشته ← کدال (خودکار حداکثر هر ۳ ساعت) | وگرنه «کامل و به‌روز»
- fresh.financial: مثل بالا؛ دوره‌های جاافتاده‌ی سال جاری، و «جدیدتر» = آخرین پایان فصلِ گذشته‌ی سال مالی شرکت
- fresh.market (رتبه‌بندی رشد سود): خوراک کل بازار خودکار حداکثر هر ۶ ساعت، دکمه‌ی کاربر همیشه
  (رتبه‌بندی ماهانه تصمیم خودش را دارد: mrank.need_scan، پایین‌تر)؛
  حتی در آن صورت فقط گزارش‌هایی که در دیتابیس نیستند دانلود می‌شوند
- POST …/fetch و …/scan: ?auto=1 = درخواست خودکار صفحه، بدون آن = دکمه‌ی کاربر (مهلت‌ها نادیده)، ?force=1 = بدون بررسی؛
  کافی بودن دیتابیس ← {"fresh": true, "message"} و هیچ درخواستی به کدال نمی‌رود.
  GET /api/monthly، /api/quarters، /api/screener، /api/mrank فیلد db = {checked, need, note} دارند ← Bourse.dbNote
- اطلاعیه‌ها هم ذخیره می‌شوند (letters)؛ search.stored_letter قبل از جستجوی نماد در کدال نگاه می‌کند
  (مرحله‌ی ۲ رتبه‌بندی‌ها؛ هر نماد حداکثر روزی یک جستجو: checks «screener_prev» / «mrank_prev»)
- خوراک کل بازار (search بدون Symbol) همه‌ی صفحه‌هایش مهلت ۳ ساعت دارند (جابه‌جا می‌شود)
- خواندن دوباره‌ی یک گزارش: نسخه‌ی قبلی فقط بعد از دریافت موفق جایگزین می‌شود (save_monthly / save_financial
  اول همان tracing_no را پاک می‌کنند)، تا کپچا وسط کار داده‌ای را پاک نکند

## کپچا بدون وقفه (کار منتظر می‌ماند، تمام نمی‌شود) و محدودیت 429 جستجو
- client.get_text صفحه‌ی «تأیید کاربر» را می‌شناسد (looks_captcha: ReportsCaptcha.aspx / captchaImage) و await_captcha()
  را صدا می‌زند: CAPTCHA_WAIT (در jobs._run: state="captcha" و client.wait_captcha_solved) تا کد اپراتور صبر می‌کند و
  بعد همان درخواست دوباره فرستاده می‌شود — کار از همان گزارش ادامه می‌دهد (نه شروع دوباره). captcha_verify ← notify.
  مهلت CAPTCHA_EXPIRE (۳۰ دقیقه)؛ بعد از آن کار با resume متوقف و با کد درست اول صف (jobs.enqueue front=True)
- 429/403 روی صفحه‌ی گزارش ← فوراً کپچا (نه صبر ۳۰/۶۰/۱۲۰ ثانیه)
- 429 جستجو (search.codal.ir) بر اساس IP است و کپچا ندارد (آزموده شد: بدون کوکی هم 429؛ بدنه «The custom error module…»)
  ← Throttled: نسخه‌ی حافظه اگر هست، وگرنه انتظار آشکار پله‌ای ۱/۲/۴/۸/۱۰ دقیقه (THROTTLE، _throttle_gate) و پس از
  ۳۰ دقیقه خطا. در این مدت هیچ درخواست جستجویی نمی‌رود. DELAY جستجو ۲٫۵ ثانیه
- GET /api/captcha: pending، since (تغییرش = کپچای تازه)، jobs (name)، throttle {active, seconds}
- app.js هر ۱٫۵ ثانیه می‌پرسد؛ Bourse.api هر پاسخی با job.state=captcha را فوراً به پنجره خبر می‌دهد (Bourse.checkCaptcha).
  «کوچک کردن» ← نوار ثابت زرد پایین صفحه («وارد کردن کد امنیتی»)؛ کپچای تازه پنجره را دوباره باز می‌کند.
  محدودیت جستجو ← نوار سفید پایین با شمارش معکوس تا ادامه‌ی خودکار
- خط فرمان: client.CAPTCHA_WAIT = ask_captcha (کد همان لحظه از ترمینال، ادامه از همان گزارش)

## کپچا در همه‌ی بخش‌ها
- هر کار کدال (عملکرد ماهانه، برآورد سود، سابقه‌ی مدل، رتبه‌بندی سود، رتبه‌بندی ماهانه) در کپچا state="captcha"
  می‌گیرد و بعد از کد درست از سر گرفته می‌شود. جستجوی کدال هم اگر صفحه‌ی کپچا بدهد (get_json) همین‌طور.

### عملکرد ماهانه (منبع: گزارش‌های فعالیت ماهانه‌ی کدال)
- صفحه‌ی اول (بدون ?symbol=): فهرست نمادها به ترتیب بیشترین تغییر درآمد (codal/mrank.py، GET /api/mrank)
  با چهار معیار قابل انتخاب (localStorage «bourse-mrank-metric»): نسبت به ماه قبل (پیش‌فرض)، میانگین ماه‌های قبل
  همان سال، ماه مشابه سال قبل، تجمعی نسبت به مدت مشابه. رتبه = ترتیب ردیف‌های دارای همان معیار.
  کلیک ردیف / جستجوی نماد (کادر بالا یا پنجره‌ی «/» در خانه) ← گزارش همان نماد؛ «فهرست نمادها» و «عملکرد ماهانه»
  نوار کناری ← بازگشت به فهرست
- گزارش ماهانه ستون‌های تجمعی را هم دارد: cum، cum_prev (تا پایان ماه قبل، اصلاح‌شده)، cum_ly (مدت مشابه)
  در monthly_reports؛ گزارش‌های قدیمی‌تر با mrank.backfill از cache.db (بدون شبکه) تکمیل می‌شوند
- رتبه‌بندی بر اساس «ماه گزارش» (ماه تقویمی پایان دوره؛ انتخابگر ماه، localStorage «bourse-mrank-month»؛ پیش‌فرض ماه گذشته).
  GET /api/mrank?month=1405-06 ← rows همان ماه، months (۱۲ ماه + تعداد شرکت‌ها، done)،
  meta {count, ranked, known_missing, prev: {wait, none, bad}}
- پایه‌ی معیارها (mrank.metrics): «نسبت به ماه قبل» = گزارش ماه قبل (ماه دوم سال مالی: cum_prev همین گزارش)؛
  «ماه مشابه سال قبل» = گزارش پارسال، وگرنه cum_ly این گزارش − cum_ly گزارش ماه قبل (ماه اول سال مالی: خود cum_ly) ←
  با گرفتن ماه قبل، این معیار هم بدون دانلود گزارش‌های پارسال کامل می‌شود. cum_ly کمتر از cum_ly گزارش ماه قبل
  (اشتباه ورود داده‌ی شرکت، مثلاً سصفها شهریور ۱۴۰۵) ← bad_ly: g_cum فقط با cum_ly ماه قبل + گزارش پارسال، وگرنه خالی
- مشکل قبلی (کاربر گزارش داد: «فقط ۵ نماد رتبه دارند و درصد رشد خالی است»): scan فقط گزارش‌های خود ماه را می‌گرفت و
  گزارش ماه قبل (پایه‌ی رشد) فقط با دکمه‌ی جدا ← حالا جزو همان دریافت است و خودکار
- scan (کار «mrank»، POST /api/mrank/scan?month=&budget=N|all): همه‌ی گزارش‌های لازم ماه که در دیتابیس نیستند، سه مرحله:
  ۱) گزارش ماه قبلِ نمادهای فهرست (waiting_prev) ۲) گزارش‌های تازه‌ی ماه ۳) ماه قبلِ نمادهای تازه. هر مرحله اول اطلاعیه‌های

- مفروضات فصل‌های گزارش‌نشده دو حالت دارد (st.mode، کلید seg «منبع مفروضات»):

     می‌شود)؛ فصلی که مدل پیشنهاد نداد با مفروضات دستی همان فصل حساب می‌شود (mlMissing + هشدار).
     «ویرایش دستی همین ارقام» (mlToManual) ← assumpFrom: یک ردیف فروش + نسبت‌ها که دقیقاً همان سود را می‌سازد، و حالت دستی
  2. «ورود دستی مفروضات» (manual): هر فصل گزارش‌نشده مفروضات جدا دارد: st.qa[i] = {products, sc}؛ زبانه‌ی فصل‌ها
     (st.qaSel، فقط فصل‌های ≥ مرحله) با EPS هر فصل، «کپی مفروضات این فصل به فصل‌های بعد»، افزودن/حذف محصول برای همان فصل.
     تعداد سهام مشترک است (st.sc.shares، کادر بالای صفحه). مدل‌های قدیمی ذخیره‌شده با normalize() یک مجموعه را به هر چهار فصل می‌دهند
- صورت سود و زیان (st.isView): «فصلی» (چهار فصل + سال)، «تجمعی» (۳، ۶، ۹، ۱۲ ماهه = جمع فصل‌ها مثل کدال)، یا یک دوره‌ی
  ۳/۶/۹/۱۲ ماهه با فصل‌هایش و ستون جمع؛ «٪ از درآمد» نسبت به آخرین ستون؛ برچسب ستون: واقعی / واقعی + پیش‌بینی / پیشنهاد مدل / مفروضات دستی
- مراحل ابتدای سال / ۳ / ۶ / ۹ / ۱۲ ماهه و کارت چهار فصل (واقعی/پیشنهاد مدل/مفروضات دستی)
- پنج کاشی: EPS سال، EPS تحقق‌یافته، P/E آتی، قیمت هدف، پتانسیل بازدهی
- جدول ورودی داده‌های واقعی فصل‌ها، مفروضات (محصولات + چهار گروه)،
  صورت سود و زیان فصلی و سالانه، و جدول ثبت و بازنگری برآوردها
- فرمول‌ها: هزینه‌ی مالی فصل = مانده × نرخ ÷ ۴؛ مالیات فقط روی سود مثبت؛
  قیمت هدف = EPS سال × P/E هدف
- ذخیره در localStorage: کلید eps-quarterly-model-v1 (مدل نمونه) و eps-quarterly-model-v1:<نماد>
  (هر نماد مدل جدا)؛ فوکوس بعد از ویرایش حفظ می‌شود
- نماد صفحه‌ی خانه مشترک است: کادر جستجوی بالا ← رویداد «bourse:symbol» ← هر دو زبانه
- اتصال به کدال: GET /api/quarters/<نماد>?fy= ← فصل‌های تحقق‌یافته از fin_latest غیرتلفیقی
  (فصل n = دوره‌ی n×۳ ماهه − دوره‌ی قبل؛ فیلدها با قرارداد مدل: هزینه‌ها مثبت، خالص‌ها با علامت)،
  stage = فصل‌های پشت سر هم، shares = سرمایه ÷ ۱۰۰۰، price = پایانی TSETMC؛ نبودِ داده ← دریافت خودکار
  (POST /api/quarters/<نماد>/fetch، کار پس‌زمینه‌ی financial در codal/collect.py)
- applyCodal: فصل‌های کدال در actuals نوشته می‌شوند و مرحله جلو می‌رود (اگر کاربر در همان سال دستی
  جلوتر رفته، دست نمی‌خورد)؛ مدل تازه‌ی هر نماد با «تکرار آخرین فصل واقعی» مقداردهی می‌شود (seedFrom)
- کنترل: EPS تجمعی گزارش‌شده‌ی کدال کنار EPS محاسبه‌ی مدل نمایش داده می‌شود
- کارهای کدال در صف سرور اجرا می‌شوند (jobs.enqueue / jobs._work): هم‌زمان یکی؛ درخواست تازه «queued» با پیام
  «در صف: بعد از …» و بعد خودکار اجرا می‌شود (دیگر 409 نیست)؛ کار تکراریِ در صف/در جریان اضافه نمی‌شود.
  هر خطایی (حتی باز کردن دیتابیس) کار را error می‌کند و صف ادامه می‌دهد. db.connect با timeout=30
- خروجی سرور: درخواست‌های دوره‌ای موفق GET /api/… چاپ نمی‌شوند (_QuietPolls)

## پیش‌بینی با یادگیری ماشین و یادگیری تقویتی (forecast.py — فقط کتابخانه‌ی استاندارد)
- تقسیم زمانی ۷۰/۲۰/۱۰ (split_idx؛ بدون بُر زدن): آموزش | اعتبارسنجی (پیش‌بینی یک‌گام walk-forward،
  انتخاب ابرپارامتر، آموزش عامل RL) | آزمون (فقط گزارش دقت)؛ پیش‌بینی آینده با برازش دوباره روی کل داده
- مدل‌ها: سری مثبت (فروش/درآمد): snaive_g، holt (هولت-وینترز روی لگاریتم)، ridge (وقفه‌های ۱-۳ و فصلی)، naive؛
  سری با علامت/نسبت: mean، snaive، ewma، naive
- عامل RL: Hedge (راهزن چندبازویی با اطلاعات کامل)، پاداش = −خطای نسبی، η ∈ {0.5, 2, 6} روی اعتبارسنجی
- معیار خطا WAPE؛ بازه‌ی پیش‌بینی = ± خطای آزمون عامل × √(1 + گام/فصل)
- monthly_forecast: فروش ماهانه (آخرین بخش پیوسته، شکاف ≤۲ ماه درون‌یابی)، افق تا پایان سال مالی
- quarterly_forecast: درآمد (اگر فروش ماهانه هست: ضریب کالیبره × فروش واقعی/پیش‌بینی ماه‌های فصل)،
  بهای تمام‌شده و هزینه‌ی فروش نسبت به درآمد، سایر اقلام مقدار، مالیات نرخ مؤثر؛
  آزمون ترکیبی سود خالص روی بخش آزمون
- API: GET /api/ml/monthly/<نماد>، GET /api/ml/quarters/<نماد>، POST /api/ml/<نماد>/history?years=5
  (کار پس‌زمینه‌ی «history»: ماهانه + صورت مالی با collect(years=...))
- عملکرد ماهانه: میله‌های هاشور «پیش‌بینی مدل» در نمودار (قابل خاموش کردن) + پنل دقت و پیش‌بینی
- برآورد سود: پنل پیشنهاد + حالت «پیش‌بینی یادگیری ماشین» در مفروضات (st.mode="ml"؛ st.useML قدیمی فقط در مهاجرت)؛
  compute() فصل‌های گزارش‌نشده را از st.mlQ می‌سازد (برچسب «پیشنهاد مدل»). وقتی کار کدال نماد در صف است،
  پیش‌بینی از داده‌ی همان دیتابیس بارگذاری می‌شود و بعد از کار دوباره ساخته می‌شود
- داده‌ی کم: کمتر از ۳۶ ماه / ۱۲ فصل هشدار و دکمه‌ی «دریافت سابقه‌ی ۵ ساله»؛ زیر ۶ نقطه فقط پیش‌بینی ساده
- خط فرمان: python scrape.py history فولاد --years 5

## رتبه‌بندی رشد سود خالص (/screener، codal/screener.py)
- آخرین صورت سود و زیان غیرتلفیقی هر شرکت (فقط symbols.type=1؛ صندوق/کارگزاری حذف)
- هر گزارش ستون‌های مقایسه‌ای دارد که در fin_reports ذخیره می‌شوند: rev_ly, net_ly (مدت مشابه سال قبل)،
  net_ly_full (کل سال قبل)، ly_end، ly_full_end. در گزارش سالانه دو ستون هم‌تاریخ هست («مدت مشابه»
  صفر و «کل سال» پر) ← مقدار غیرصفر برداشته می‌شود
- پارامتر ۱: رشد سود دوره نسبت به مدت مشابه؛ پارامتر ۲: فصل آخر (دوره − دوره‌ی قبل همان سال) نسبت به
  فصل مشابه (ستون سال قبلِ همان دو گزارش) و نسبت به فصل قبل (برای ۳ ماهه: کل سال قبل − ۹ ماهه‌ی سال قبل)؛
  پارامتر ۳: سود دوره ÷ سود کل سال قبل
- رشد با پایه‌ی منفی = (جاری − پایه) ÷ |پایه|؛ پایه‌ی صفر ← بدون مقدار
- امتیاز: صدک هر معیار؛ p1 = صدک رشد دوره، p2 = میانگین صدک دو رشد فصلی، p3 = صدک «تحقق ÷ (ماه‌ها/۱۲)»؛
  امتیاز = میانگین پارامترهای موجود (p1 الزامی)؛ گزارش قدیمی‌تر از ۱۲ ماه رتبه ندارد
- scan(): مرحله‌ی ۱ خوراک کل بازار (search بدون Symbol، LetterType=6، جدیدترین اول) ← آخرین گزارش هر شرکت؛
  مرحله‌ی ۲ گزارش‌های قبلی لازم برای پارامتر ۲ (و تکمیل گزارش‌های بدون ستون مقایسه‌ای)؛ budget = تعداد گزارش
- کار پس‌زمینه‌ی «screener» (POST /api/screener/scan?budget=)؛ GET /api/screener (?top=N)؛
  رتبه‌بندی با کلید (تعداد، آخرین id، آخرین fetched_at) کش می‌شود
- جستجو: کادر خالی ← ۶ رتبه‌ی برتر؛ نتیجه‌ها نشان «رتبه n» (لینک به /screener?q=)
- خط فرمان: python scrape.py screen --limit 150
